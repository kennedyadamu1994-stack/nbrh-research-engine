# The NBRH Research Engine — Technical Spec

This is the architecture document for the Option B build: a standalone repo on Vercel/GitHub that orchestrates verified research runs against your Google Sheets, with a review dashboard for your approve/reject workflow. This is the backbone system, so the spec below is written to be robust rather than fast to ship. Build order is at the end.

---

## 1. Scope decision: which columns this tool actually touches

Before anything else, every column across your 14 worksheets needed sorting into what a research tool should and shouldn't be responsible for. Filling in the wrong kind of field with AI-generated content is a real risk here (a fabricated influencer rate card or a guessed safeguarding claim is worse than a blank cell), so this classification is the foundation the rest of the system sits on.

**Four categories:**

- **RESEARCH** — the tool actively searches for, verifies, and populates this from the web.
- **SYSTEM** — auto-generated by the pipeline itself (IDs, timestamps, computed scores). Never hand-written by the AI's research pass.
- **EDITORIAL** — a judgment call that belongs to you or your team (ratings, vibe, sponsorship status, pipeline stage). The tool never fills these in.
- **DERIVED** — computed from other fields already in the row (e.g. lat/long from an address, total price from base price minus discount). Handled by a small utility function, not a research call.

### Universal columns (present on nearly every sheet)
| Column | Category | Notes |
|---|---|---|
| `record_id` | SYSTEM | Assigned on insert |
| `date_added` | SYSTEM | Timestamp on insert |
| `last_updated` | SYSTEM | Timestamp on any edit |
| `added_by` | SYSTEM | "research-engine" or a reviewer's name on manual edit |
| `source_url` | SYSTEM | Populated from the research step's own citations |
| `credibility_score` | SYSTEM | Computed from proof points, never asserted directly by the model |
| `verification_status` | SYSTEM | Derived from credibility_score against your threshold |
| `tags` | RESEARCH | Low-stakes, safe to auto-populate |
| `U notes` | EDITORIAL | Your own internal notes |
| `PREMIUM/CORE` | EDITORIAL | Monetization tier, not a fact about the entity |
| `SPONSORED?` | EDITORIAL | Commercial arrangement |
| `IN/EX` | EDITORIAL | Your include/exclude call |
| Image/gallery URLs | RESEARCH | Sourced alongside the rest of the row |

### Per-worksheet classification

**Sessions** — Research: activity type, club, class name, date/time/duration, address, location, base price, booking URL, website, age group, equipment provided, cancellation policy, indoor/outdoor, days, booking type, transaction fee. Derived: total price (base minus discount), lat/long. Editorial (NBRH's own rating system, not researchable facts): difficulty level, spots available, badge, audience, NBRH rating, vibe, and all six sub-scores (sportsmanship, organisation, competitiveness, equipment/venues, friendliness, skill level), review count, session status, sponsored, type.

**Leagues & Clubs** — Research: name, active status, page/booking URLs, activity type, location, fees, member count, sessions per week, up to 4 session slots, bio, coach name/role, facilities, contact details (email/phone/whatsapp/instagram/website), address, gallery images, pay-per-session price. Derived: savings amount. Editorial: logo emoji, star rating, confidence score, ranking position/category, average attendance, member growth, all testimonials (real quotes should never be fabricated by an AI — if used at all, these need to come from actual sourced reviews, flagged and reviewed manually, never generated), all benefit blocks and FAQs (this reads as marketing copy your team writes, not researched fact), tags (who/vibe/accessibility), teams list.

**Neighbours** — **Out of scope entirely.** This sheet holds personal data on your own members (name, email, DOB, gender, disability status, phone). A research tool has no business populating or touching this sheet. Flagging this explicitly so it's a deliberate exclusion, not an oversight.

**Venues & Social Venues** — Research: name, type, operator, public/private, full address, borough, nearest station and walk time, parking, sports supported, indoor/outdoor, surface, court/pitch count, changing rooms, showers, accessibility, spectator space, open days/hours, booking requirements, price band, hourly rates, contact details, Google Maps URL. Derived: lat/long. Editorial: internal verification flag, written descriptions, vibe tags, "best for" copy, editor notes. `Column 55` is unlabeled in your sheet — flagging for you to identify before build.

**Events** — Research: name, type, format, sport(s), skill level, age groups, gender policy, team/individual, location, dates/times, duration, max participants, price, concessions, equipment, organiser details, contact info, booking URL, cancellation/refund policy. Editorial: current participant count (changes too fast to hand-research), written descriptions, vibe tags, safety notes, internal notes.

**Influencers** — Research: name/handle, platforms, follower count, engagement rate, niche, location, sports covered, content type, past collabs, contact method, agent/management. **Editorial, not research (fabrication risk):** audience demographics and rate card/estimated cost are rarely public — asking a model to "find" these produces confident-sounding guesses rather than facts. Also editorial: availability, authenticity flags, content rights, exclusivity terms, fit score.

**Brands** — Research: name, industry, company size, sports focus, existing agency, activation history, past grassroots activity, contact details, HQ location. Editorial (require direct conversation, not web research): marketing budget signal, CSR/ESG mandate, partnership type sought, decision-making cycle.

**Businesses** — Research: name, type, location, owner/contact details. Editorial: everything assessing fit with NBRH (community engagement level, foot traffic relevance, reciprocity potential, audience overlap, budget tier) — these are your judgment calls, not facts.

**Funding** — Research: fund name, body, type, amount range, recurring/one-off, eligibility, co-funding requirement, deadline, geographic/sector restriction, application link, past success examples, contact. Editorial (semi-derivable but treat as a draft, not a fact): application complexity, reporting burden.

**People** — Research: name, professional type, primary sport, location, bio, booking URL, website, experience, certifications, specialisation, price per hour, availability, age groups. Editorial/System: user rating and review count (tied to NBRH's own review system, not external research), verified/active flags.

**Kit** — Research: supplier name, product categories, brands carried, price tier, bulk discount, customization, sustainability credentials, sample availability, lead time, minimum order, delivery area, contact, past clients. Editorial (needs real documentation, not just a search — flagging as high-risk if asserted wrongly): safeguarding compliance.

**Sponsorships** — Research: opportunity name, offering entity, type, inventory type, duration, expiry, sport, location, contact. Editorial: package value and reach/exposure estimate (rarely public without direct inquiry), status (your pipeline tracking).

**Opportunities** — Research: title, type, sport(s), organisation, borough, frequency, description, requirements, experience level, DBS requirement, paid/unpaid, dates, hours per week, contact details, application link. Editorial/System: status, internal notes.

## 2. System architecture

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  Trigger         │────▶│  Research Engine  │────▶│  Review Queue    │
│  (manual /       │     │  (API route,      │     │  (dashboard UI)  │
│   scheduled)      │     │   calls Claude    │     │                  │
└─────────────────┘     │   w/ web search)  │     └────────┬────────┘
                          └──────────────────┘              │
                                    │                        │ approve/reject
                                    ▼                        ▼
                          ┌──────────────────┐     ┌─────────────────┐
                          │  Staging table    │     │  Google Sheets   │
                          │  (pending review) │     │  (live data)      │
                          └──────────────────┘     └─────────────────┘
                                    ▲                        │
                                    │                        │
                          ┌─────────┴────────────────────────┘
                          │  Rejection memory (feeds back into
                          │  future runs so rejected entities
                          │  aren't resurfaced)
                          └────────────────────────────────────
```

### 2.1 Stack
- **Framework:** Next.js on Vercel, matching the existing Engine repo.
- **Data layer:** Google Sheets as the live database, per your decision. One tab per worksheet, matching current structure exactly.
- **Staging layer:** A new, separate "Pending Review" Google spreadsheet (not tabs inside the live spreadsheet), holding rows the research engine has produced but you haven't approved yet. Nothing lands in the live tabs without passing through here first. Keeping it as its own spreadsheet means the live data your Engine and Club House OS actually read from is never at risk of accidental exposure to in-progress or rejected rows, and it keeps permissions simple, you can share the staging sheet with a reviewer without giving them edit access to live data.
- **Rejection memory:** A dedicated tab (`_rejected_log`) storing entity name, worksheet, date rejected, and your reason if given. The research engine reads this before every run and is instructed to skip anything matching.
- **AI backend:** Claude via the Anthropic API with web search as a tool. This replaces the Perplexity option from Part 1 — Perplexity doesn't currently expose a public Deep Research API you can call this way, so Claude's API with the web search tool is the only realistic backend for an automated version of this.
- **Auth:** Simple password gate or your existing Vercel account auth, matching how the Engine is currently locked down.

### 2.2 Why a staging layer matters
This is the single most important structural decision in this spec. Your original memo describes wanting to review everything yourself before it's "real" data. If the research engine writes straight into your live Sheets, you lose that checkpoint and a bad run can pollute data that Club House OS or the public Engine is actively reading from. Staging makes "run research" and "publish to live data" two distinct, separately-triggered steps.

### 2.3 Confidence scoring, carried over from the prompt work
The per-field confidence tiers and proof-point requirement from the prompt spec apply here too, but now they're structured data instead of prose in a chat response:
- Each staged row carries a `credibility_score` (0-100), `verification_status` (Verified / Likely Active / Probably Active / Uncertain / Unconfirmed), a `source_url` per populated field where feasible, and a `proof_points` field (short text list).
- The dashboard sorts the review queue by confidence, so you can process high-confidence rows fast and give the borderline ones more attention.
- As discussed previously: the score is a triage aid computed from proof points, not a verified fact. The proof points and source URLs are what's actually checkable.

### 2.4 Feedback loop
Every approve/reject action in the dashboard writes to a `_feedback_log` tab: entity, worksheet, decision, timestamp, and an optional note from you (e.g. "wrong borough," "listing is dead," "this is exactly right"). This is the piece your original memo specifically asked for. Two uses:
1. **Rejection memory** (2.1 above) — stops the same bad entity resurfacing.
2. **Prompt tuning input** — periodically, patterns in your rejection notes (e.g. if you keep rejecting entries sourced only from Instagram) get reviewed and folded back into the research engine's instructions. This is a manual review step for you or me to do monthly, not an automated fine-tuning loop — that's a much bigger undertaking and not what's being proposed here.

## 3. Research engine behavior

The instructions this component runs on are a structured, machine-executed version of the prompt already validated in the earlier brief. Key carry-overs:
- Minimum candidate count checked per run (your call per run, not hardcoded).
- 3-4 independent proof points required per entity before it's staged at all.
- Per-field confidence, not just per-row.
- Explicit fetch-and-read of each candidate page, not reliance on search snippets alone.
- Name-collision disambiguation for common club/league names.
- "Not found" reporting when a category comes up thin, so a short result reads as signal rather than failure.
- Never fills RESEARCH-ineligible fields — the classification in Section 1 is enforced at the code level (the engine literally isn't given those columns to populate), not just requested politely in a prompt.

## 4. Review dashboard

Minimum viable version:
- List view of the pending-review staging tab, filterable by worksheet and sortable by confidence score.
- Per-row detail view showing every populated field, its source URL, and its confidence tier.
- Approve / Reject / Approve-with-edit actions. Edits get logged as your correction, feeding the same feedback log.
- A "not found" panel per run showing what the engine searched for and couldn't verify, so you can see the gaps.
- Basic run history: what was run, when, how many candidates checked, how many staged, how many you ultimately approved.

Not in scope for v1: bulk approve, auto-approve above a confidence threshold. Given this is meant to become the backbone dataset, everything should pass through your eyes at least for the first several months, per the hybrid approach already agreed. Automation of the approval step itself is a later conversation once you trust the confidence scoring in practice.

## 5. Decisions confirmed

1. **Column classification (Section 1) is approved as written.** Influencer rate cards/demographics, brand budget signals, and safeguarding compliance stay out of the AI's research scope, since they're rarely public and a model asked to "find" them tends to produce a confident-sounding guess rather than a real gap.
2. **`Column 55`** on Venues and Social Venues is ignored entirely, it's dropped from the engine's target column list on both sheets so nothing ever gets written there.
3. **Run cadence:** manual trigger only to start. No scheduled/automatic runs until the engine has proven itself over a stretch of manual use. This also keeps you in direct control of API spend, since every run is something you chose to kick off.
4. **Budget:** under £50/month for Claude API calls. This is a real constraint on how the engine is built, not just a nice-to-have, and shapes a few decisions directly: default candidate-check counts per run should stay modest (roughly 15-20 rather than searching exhaustively), each run should log its actual token/search cost so you can see spend accumulate in real time rather than finding out at the end of the month, and a simple running-total safeguard should stop new runs once you're approaching the £50 mark for that month, with an override if you want to push past it deliberately.
5. **Staging structure:** a new, separate Google spreadsheet for pending-review data, not tabs in the live sheet. Reflected in Section 2.1 above.

## 6. Build order

All open questions from the previous draft are resolved (Section 5), so this is now the actual build sequence rather than a proposal.

1. Scaffold the repo (Next.js, Vercel, auth) — no research logic yet, just the shell and Sheets connection.
2. Create the new staging spreadsheet, plus the `_rejected_log` and `_feedback_log` tabs within it.
3. Build the research engine as a single-worksheet API route (starting with Venues or Clubs, since those map cleanest to your existing Engine confidence-scoring precedent), including the per-run cost logging and the £50/month running-total safeguard from Section 5. Test it end to end: manual trigger → staged rows with cost logged → manual approve → lands in live Sheets.
4. Build the review dashboard around that one worksheet.
5. Once one worksheet works end to end, extend the engine to the remaining 12 in-scope worksheets (Neighbours excluded per Section 1), reusing the same pipeline with per-worksheet column configs, each respecting the RESEARCH/SYSTEM/EDITORIAL/DERIVED split already agreed.
6. Run it for real for a few weeks on manual trigger, use the feedback log to spot patterns, tune the engine's instructions. Revisit scheduled runs only once you're satisfied with output quality and comfortable with actual observed cost per run.
